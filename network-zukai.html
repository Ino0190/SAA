AWSをお店に例えると（全体地図）

AWSは「インターネット上のお店をつくる道具一式」。クラウド＝場所を借りてお店を開く感じ。各サービスはお店の中の役割に対応する。下の地図のクリックで、その役割の詳しい図にジャンプする。

⭐ = お店の地図には部屋として描いてないが本番頻出の専門室。「火事に強い建物 = 高可用」「予備の店 = DR」「待ち時間ゼロカウンター = 性能・キャッシュ」と読み替える。

🏪 Storage Gateway 2種の対比＝主はどっち？

問題文の「主データはどこか」で2種が決まる。「クラウドで容量増やしたい」=キャッシュ型、「オンプレで運用継続+AWSにバックアップ」=ストアド型。

決め手の1語：問題文に「クラウド容量を増やしたい」「主はクラウド」 → キャッシュ型／「オンプレで運用継続」「DR用バックアップ」 → ストアド型。

🌊 データの川（Flink ＋ DataZone）

「リアルタイム異常検知＝Flink」「部門間データ共有＝DataZone」を1枚に。データが川のように流れて、見張られて、保管されて、別の部門に売られる。

🏘️ マイクロサービス＝役割分担した小さな係（VPC Lattice ＋ EKS Auto Mode）

マイクロサービスとは？＝1つの仕事を、役割ごとに分けた小さな係（小さなアプリ）で分業する作り。たとえばオンラインショップなら「注文係・在庫係・決済係・配送係…」と分ける。

係どうしは何をしてる？＝1件の仕事（例：1つの注文を完結させる）を、係どうしが順番に会話して仕上げる。下の絵で「1つの注文がぐるぐる係を回って完結する流れ」を見る。

2サービスの役割の違い

サービス役割たとえ
VPC Lattice係どうしが別アカウントを超えて会話できる連絡網会社の社内インターホン（部署を越えて繋がる）
EKS Auto Mode各係（マイクロサービス）を動かす土台＝Kubernetesを、AWSが完全に運営係が働く事務所をAWSが用意・管理してくれる

つまり：EKS Auto Mode = 事務所（土台）／VPC Lattice = 事務所どうしを繋ぐ社内インターホン。両方セットで使うのが「マイクロサービスをアカウント超えて運用」の王道。

なぜわざわざ係に分ける？（モノリス vs マイクロサービス）

代わりに係どうしの会話の経路が必要 → そこに VPC Lattice の出番。係が動く土台として → EKS Auto Mode の出番。

決め手の1語：「マイクロサービス＋複数アカウント＋サービスディスカバリ」=VPC Lattice／「Kubernetes＋運用負荷最小」=EKS Auto Mode。

📞 係どうしの会話は2方式（直接喋る vs メモで頼む）

マイクロサービス間通信には2つのやり方がある。「即答えが要るか／頼んで終わりでいいか」で使い分ける。

使い分けの決め手
こんな時方式
「答えが返ってこないと次に進めない」（在庫確認・決済処理・認証）直接喋る（VPC Lattice / HTTP）
「頼んで終わりでいい」（メール送信・ログ記録・後続処理）メモで頼む（SQS等）
「処理が時間かかる」「重い処理」メモで頼む（SQS）= 自分は次の仕事へ
「相手が落ちても再処理したい」「耐障害性」メモで頼む（SQS）= 箱に残る

📨 メモで頼む4サービス（SQS / SNS / EventBridge / Step Functions）

「メモで頼む」道具は4種類。誰に届けるか・何を運ぶかで使い分け。

4サービスの使い分け（決めの1語）
サービスたとえこう問われたら
SQS順番箱（伝言板）「1対1で順番に処理」「キュー」「耐障害性・再処理」
SNS全員に放送（拡声器）「1つの出来事を関係者全員に通知」「ファンアウト」「メール+SMS+Lambda同時」
EventBridge郵便仕分け係（条件で配り分け）「イベントをルールで振り分け」「AWSサービス連携」「サードパーティSaaSイベント」
Step Functions業務フロー司令官「複数ステップの順番を管理」「分岐・リトライ・並列」「ワークフロー全体」

混同しやすい3組：

  • SQS vs SNS：SQSは1対1（箱から1人が取る）／SNSは1対多（全員に同時に放送）
  • SNS vs EventBridge：SNSはシンプルに全員放送／EventBridgeは条件で振り分け＋AWSサービス間連携が本職
  • Step Functions vs SQS/SNS/EventBridge：Step Functionsは手順全体を管理する司令官。他3つは「メッセージを運ぶ運搬役」だが、Step Functionsは「運搬役を呼びながら手順を管理する上の人」

コンピュートの選び方（EC2 / Fargate / Lambda）

軸は1本＝「どこまで自分で管理するか（自由）↔ どこまでAWSに任せるか（手軽）」。左ほど自由で手間大、右ほど手軽で制約あり。下のボタンで「こう問われたら」を押すと該当が強調される。

ボタンを押すと、その状況で選ぶべきサービスだけ強調されます。
判断3問（順に当てるだけ）
問いYesなら
① OSを自分で触る必要がある？（特殊設定・常時稼働・GPU）EC2
② コンテナを使う？ サーバー管理はしたくない？Fargate（k8sならEKS on Fargate）
③ イベントで短時間動くだけ？（ゼロもある・管理ゼロ）Lambda（最大15分に注意）

たとえ：EC2＝一軒家（全部自分で管理）／Fargate＝家具付き賃貸（建物の管理は大家）／Lambda＝必要な時だけのレンタルスペース（使った分だけ・長居は不可）。

コンテナは2層構造（EC2とECSは別の層）

ECS/EKS＝コンテナを束ねて管理する司令塔。実際にコンテナを動かす土台として、EC2（自分のサーバー群）か Fargate（サーバー管理なし）を選ぶ。だからEC2とECSは「どっちか」でなく別の層。

見分け：コンテナを使う→ECS（k8sならEKS）。その上でサーバー管理したくない→Fargate、EC2を細かく制御したい→EC2起動タイプ。コンテナを使わず普通のサーバー1台でOSを触りたい→そのままEC2。

CloudFront vs Global Accelerator

どっちも「エッジを使って世界中のユーザーを速くする」と説明されるので混同する。違いは一点 ── コンテンツをキャッシュ（コピー）するか／しないか。

CloudFront＝コンテンツを近くに置く（CDN）

Global Accelerator＝速い道に乗せる

タイプ性質・使いどころ
gp3（汎用SSD）標準の選択肢。多くのワークロードはこれ。IOPS/スループットを容量と独立に設定できコスパ良い
io2 / io2 Block Express（プロビジョンドIOPS SSD）最高のIOPS・低レイテンシが必要な大規模DB（高負荷のRDBMS等）。「プロビジョンドIOPS」「ミッションクリティカルなDB」で選ぶ
st1（スループット最適化HDD）大きなファイルを順番に読むシーケンシャル・大容量スループット（ビッグデータ、ログ処理）。安い
sc1（コールドHDD）アクセス頻度が低い大容量データ。最安。めったに読まないアーカイブ的用途

決め手：「高IOPS・低遅延の本番DB」＝io2（プロビジョンドIOPS）／迷ったら gp3／大きいファイルを連続で・安く＝st1／めったに読まない最安＝sc1。SSD（gp3/io2）＝IOPS重視、HDD（st1/sc1）＝スループット/コスト重視。
